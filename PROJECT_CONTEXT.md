## 4. Environment and workflow

**Docker (`compose.local.yaml`) is the authoritative local environment.** The root `docker-compose.yml` is upstream's and is not used.

| Service | What it is | Notes |
|---|---|---|
| `app` | PHP/Laravel, built from `docker/local/Dockerfile` | project folder mounted at `/var/www/html`; `vendor` is a named volume |
| `web` | `nginx:stable-alpine` | bound to `127.0.0.1:8088` |
| `database` | `mariadb:10.11` | host `database` inside the Docker network only; **not published to the host** |
| `node` | `node:22-bookworm-slim` | tooling only |

- Status: `docker compose -f compose.local.yaml ps`. Stop without losing data: `docker compose -f compose.local.yaml stop`. **Never** `down -v`: it deletes the database volume.
- A Windows MySQL may also listen on port 3306. It is **not** the project database; the project login is rejected there [Verified 2026-10-25].
- Windows host PHP comes from Laravel Herd (`php.bat`). It is good for `php -l` and Pint but cannot reach the Docker database.
- `.env` holds the real values. `.env.backup-*` copies exist locally and are git-ignored [Verified]. Never print or commit them.

**Running tests safely.** The suite uses `DatabaseTransactions` against whatever database `.env` names and expects a freshly installed database. SQLite fails (the migrations use MySQL functions such as `CONCAT`). What worked on 2026-10-25: start a throwaway MariaDB container on the compose network, run `php artisan migrate --force` plus the installer's `DatabaseSeeder` (and `DatabaseManager::createAdminUser`) with environment-variable overrides for the DB settings, run Pest inside the `app` container, then delete the container. Do not use `bagisto:install` for this: it runs `key:generate` and wipes the database.

**Existing-container QA option (verified 2026-10-27):** `bagisto-local-app-1`, `bagisto-local-web-1` and healthy `bagisto-local-database-1` are already running on port 8088. A separate, freshly migrated and system-seeded database `bagisto_order_workflow_qa_20261027` now exists in the local MariaDB container; use the app container with `-e DB_DATABASE=bagisto_order_workflow_qa_20261027 -e CACHE_STORE=array -e SESSION_DRIVER=array -e QUEUE_CONNECTION=sync -e MAIL_MAILER=array` for these transactional tests. ## 11. Deployment [Owner + scripts]

Package the release from a clean worktree, upload and stage it, then the **owner** activates it as root. Every release bumps `release.json`. Hard-won checks (full list in `AGENTS.md`):
- new theme files need `git add -f`, run as its own command, then check with `git ls-files`;
- never ship files under `public/admin` (nginx returns 403 for `/admin/`); test both `/admin` and `/admin/` after a release;
- `git add` explicit paths only; never stage `*.bak`, `route-list.json`, `deploy.bat`;
- config is cached at activation; after editing production `.env` run `config:cache` and restart the queue service.

**The release path, step by step (scripts in `scripts/deploy/`, packaging/staging revised 2026-11-13):**
1. Commit on a branch with explicit `git add` paths, the owner merges to `main`, then bump `release.json` (new `release_id`, `version`, `commit`).
2. `package-release.sh /path/outside/repo/release.tar.gz` enforces a **clean worktree of `main`**, including no untracked files. It exports committed `HEAD` using `git archive`, with an explicit source-path allow-list and exclusions for tests, `.env*`, keys, backups, dependency directories, cached config, public storage and the QA product seeder. It refuses symbolic links/submodules, any `public/admin` entry, an archive inside the checkout or an existing output. Committed release metadata, Shop lockfile and all three asset manifests are required. It prints the SHA256. Use a separate clean checkout; preserve the owner's existing untracked files. `package-admin-update.sh` now requires matching, already committed `release.json` metadata and an ancestor source commit; it never rewrites the checkout and uses PHP to create the external manifest.
3. Upload as `mansecret-deploy`; `stage-release.sh <archive> <release_id> <sha256>` checks the hash and archive, links the shared `.env` and storage, runs `composer install --no-dev`, and builds **Shop** assets using its committed lockfile. **Root and Admin assets use their committed bundles**; staging requires their manifests. The old root `npm ci` step could not succeed because no root lockfile is committed; the earlier statement that its error was expected was wrong under `set -e`. That step is removed locally. No root/Admin source assets differ between this branch and `main`; future changes to them require rebuilding and reviewing their bundles before packaging.
4. Pending migrations: inspect `migrate:status`, then the owner runs `migrate-reviewed.sh <release_id> --pending-migrations-reviewed` (maintenance on, database and media backup, `migrate --force`).
5. The owner runs `activate-release.sh <release_id> --data-reviewed` as root: package discovery, `config:cache`, `route:cache`, `view:cache`, `check-production.php` (environment, HTTPS, sessions, queue, no QA products, asset manifests, storage link, listed payment methods off), a second backup, symlink switch, queue and scheduler restart. It switches back automatically if a step fails.
6. Live checks: `/`, `/admin` and `/admin/`, a product page, checkout up to the payment step, the Seller Workspace. `rollback-release.sh <previous_id> --schema-compatible` switches code back only; restoring the database is a separate decision.
